Security and architecture

Where your data goes, written down.

This page describes how DocToRecords is built and what it does with your documents, in enough detail for a Salesforce admin or security reviewer to check. If something you need is missing, ask us.

DocToRecords in one paragraph

DocToRecords is built entirely on the Salesforce Platform: Apex, Lightning Web Components and one Prompt Builder template. There is no external web service, no separate server or database, and no off-platform component of any kind. Documents and extracted data stay in standard Salesforce storage inside your org. The only processing outside the record is a call to your org's own Einstein generative AI.

What happens to a document

  1. Upload. The file is saved as a standard Salesforce File in your org.
  2. Extraction. A background Apex job sends the file and the template's instructions to your org's Einstein generative AI, through Salesforce's Prompt Builder API. That call is subject to your org's Einstein Trust Layer settings.
  3. Staging. The response is parsed, converted to each target field's type, and held in DocToRecords' own staging objects. Nothing is written to your business objects yet.
  4. Review. A person checks every value, and can edit or clear any of them. Duplicate matching only looks at fields that reviewer is allowed to read.
  5. Commit. On the reviewer's explicit action, records are inserted or updated in a single transaction. If any record fails, everything is rolled back and the reason is shown.

Controls

AreaHow DocToRecords handles it
NetworkNo HTTP callouts. No Named Credentials, Remote Site Settings or external endpoints.
CredentialsNone stored, requested or transmitted. No Connected Apps, Auth Providers, OAuth tokens or API keys.
Record sharingEvery Apex class is declared with sharing. There are no without sharing or global classes.
Object and field accessQueries run WITH USER_MODE and writes run as the user, with describe checks before every save. Nobody can read or change data through DocToRecords that they could not touch directly.
Query injectionObject and field names from template configuration are resolved against the schema and escaped. All values are bind variables.
Front endLightning Web Components only. No Visualforce, no Aura, no third-party JavaScript and nothing loaded from an external CDN.
AccessOne permission set, DocToRecords_Admin. The package changes no profiles or org settings and creates no users.
ExtensibilityThe extraction engine is chosen by a protected setting, and any class it names must implement the package's own interface or it is rejected.

What your org needs

Einstein generative AI enabled, with Prompt Builder available. DocToRecords uses only standard objects and APIs. It does not require Health Cloud or any other package.

Review status

DocToRecords is not listed on AppExchange and has not been through Salesforce's AppExchange security review. It is installed directly from a link, into a sandbox first. So that you can do your own assessment, we share the following on request:

  • an architecture and usage document;
  • the Salesforce Code Analyzer report for the package;
  • our written response to each scanner finding.

Ask for the security pack and tell us who is reviewing it. Documents with health information need your own compliance sign-off: whether your Salesforce agreement covers them is between you and Salesforce.
